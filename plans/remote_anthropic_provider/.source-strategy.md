h2. Description

The downstream llama-stack distribution does not include the {{remote::anthropic}} provider implementation that is available in upstream llama-stack. This forces users to use the generic {{remote::openai}} provider as a workaround when connecting to Anthropic API endpoints, which results in several critical compatibility issues.

h3. BUSINESS JUSTIFICATION

Anthropic's Claude models are among the most popular model providers. Proper first-class support for Anthropic models is essential for the Gen AI Studio external model feature planned for RHOAI 3.4 and for customers to use these models directly with Llamastack.

h3. CURRENT WORKAROUND AND ITS LIMITATIONS

We successfully "hacked" Anthropic to work using {{provider_type: remote::openai}} with custom network headers for authentication:

{code:java}network:
  headers:
    x-api-key: ${env.EXTERNAL_MODEL_PROVIDER_API_KEY:=placeholder}
    anthropic-version: "2023-06-01"{code}

Testing confirmed this workaround works for:

* Chat completions API (with and without streaming)
* Responses API (with and without streaming)
* MCP servers
* Tool calling
* Temperature and sampling parameters

However, this workaround has the following critical issues:

*1. AUTHENTICATION HEADER INCOMPATIBILITY*

* Anthropic does NOT accept standard OAuth bearer tokens ({{Authorization: Bearer}})
* Instead, Anthropic requires two custom headers:

  - {{x-api-key: <api_key>}}   - {{anthropic-version: 2023-06-01}}

* The {{remote::openai}} provider sends {{Authorization: Bearer}} by default
* We work around this using {{network.headers}} config, but this is not the proper solution

*2. NO PER-REQUEST API KEY OVERRIDE*

* The {{x-llamastack-provider-data}} header mechanism ({{"openai_api_key": "..."}}) successfully overrides the config API key for {{Authorization: Bearer}} headers
* However, it does NOT override custom headers set via {{network.headers}} in the config
* The {{x-api-key}} header remains static from config and cannot be changed per-request
* This blocks multi-tenant scenarios where different users need different API keys for the same provider endpoint
* For RHOAI 3.4, we may mount secrets to containers, but this prevents future per-user API token support and is a security risk

*3. ENGINEERING PRECEDENT CONCERNS*

* We do not want to set the precedent of doing custom workarounds per model provider in Gen AI Studio
* Applying {{network.headers}} to every remote model is not scalable or maintainable
* This approach creates technical debt and migration challenges when native providers become available
* Future providers (Cohere, Mistral, etc.) would require similar hacks

*4. BACKWARDS COMPATIBILITY AND MIGRATION COMPLEXITY*

* Models configured with {{network.headers}} workaround will need migration when native provider is added
* Users who set up Anthropic models in RHOAI 3.4 will need to reconfigure them in future releases
* This creates a poor user experience and support burden
* Documentation and migration guides will be complex

All functionality works with the workaround, but the per-request API key limitation is a blocker for production use cases.

h3. PROPOSED SOLUTION

Backport or include the {{remote::anthropic}} provider implementation from upstream llama-stack into the downstream RHOAI distribution. The native provider:

* Handles Anthropic-specific authentication ({{x-api-key}} + {{anthropic-version}} headers) correctly
* Properly implements model listing using {{AsyncAnthropic}} SDK (Anthropic's {{/v1/models}} endpoint returns different format than OpenAI)
* Transforms requests/responses to match Anthropic's API expectations
* Implements proper error handling for Anthropic-specific API responses
* Supports provider-specific features (e.g., Claude's thinking/reasoning capabilities)
* Enables per-request API key override via provider data headers ({{anthropic_api_key}} field)
* Provides clear guidance on embedding model recommendations (Voyage AI)

h3. IMPACT ON RHOAI 3.4 TIMELINE

The Gen AI Studio external model feature is planned for RHOAI 3.4. Without native Anthropic support:

* We can only support OpenAI models with full per-user token functionality
* Anthropic support will be severely limited (no per-user tokens, complex setup, migration issues)
* We must hardcode a limited provider list in the UI
* Migration path will be complex when native providers are eventually added
* User experience will be degraded for one of the most requested model providers

With native Anthropic support in RHOAI 3.4:

* Full feature parity across OpenAI and Anthropic
* Clean architecture without workarounds
* Smooth path to per-user API tokens from day one
* Production-quality experience for enterprise customers using Claude models

h3. TL;DR

Include the upstream {{remote::anthropic}} inference provider in the RHOAI OGX (formerly Llama Stack) distribution image, enabling native Anthropic Claude model support with proper authentication ({{x-api-key}} + {{anthropic-version}} headers), per-request API key override, and correct model listing. *Components*: ogx-distribution (formerly llama-stack-distribution), ogx-k8s-operator (formerly Llama Stack K8s Operator)

h3. Technical Approach

The upstream OGX (formerly Llama Stack) project includes a {{remote::anthropic}} provider that natively handles Anthropic-specific authentication headers, model listing via {{AsyncAnthropic}} SDK, request/response transformation, and per-request API key override via the {{anthropic_api_key}} field in provider data headers. The core task is including this provider in the downstream RHOAI distribution.

*Distribution Configuration Update.* The {{remote::anthropic}} provider must be added to the OGX distribution's {{build.yaml}} (build-time dependency declaration) and {{config.yaml}} (runtime provider activation). The {{config.yaml}} entry follows the conditional environment variable pattern: {{${env.ANTHROPIC_API_KEY:+anthropic-inference}}}, activating the Anthropic provider only when the {{ANTHROPIC_API_KEY}} environment variable is set. This mirrors how Bedrock, WatsonX, Azure, Vertex AI, and OpenAI providers are configured (architecture context: ogx-distribution.md -- provider activation pattern).

*Konflux Build Integration.* The Anthropic provider requires the {{anthropic}} Python SDK package. This dependency must be available in the AIPCC wheel release pipeline for the Konflux build ({{Dockerfile.konflux}}) to succeed. If the {{anthropic}} package is not yet in the AIPCC pipeline, it must be onboarded alongside its transitive dependencies.

*Authentication Handling.* The native {{remote::anthropic}} provider correctly sends {{x-api-key}} and {{anthropic-version}} headers (instead of {{Authorization: Bearer}}), eliminating the need for {{network.headers}} workarounds. This is a pure provider-level concern -- no changes to the OGX server framework or operator are required.

*Operator Integration.* The OGX K8s Operator (formerly Llama Stack K8s Operator) requires no code changes. The Anthropic provider is activated through environment variables set in the user's ConfigMap or CR spec, which the operator already supports for passing configuration to managed pods (architecture context: ogx-k8s-operator.md -- user ConfigMap injection).

h3. Non-Functional Requirements

* *Security*: Anthropic API keys handled through Kubernetes Secrets injected as environment variables, consistent with existing provider secret management (architecture context: ogx-distribution.md -- secrets). Per-request key override uses the {{x-ogx-provider-data}} header mechanism. TLS 1.2+ enforced for egress to Anthropic API endpoints.
* *Backwards Compatibility*: Additive change. Existing {{remote::openai}} workaround configurations continue to work. Migration to {{remote::anthropic}} is optional but recommended to get proper authentication and per-request key override.

h3. Out-of-Scope

* Anthropic-specific UI in Gen AI Studio (handled by dashboard team separately)
* Per-user API token management through the Dashboard UI (future release)
* Anthropic embedding model support (Anthropic does not provide embedding models; RFE notes guidance on Voyage AI for embeddings)
* Claude thinking/reasoning capabilities (provider-level feature; may work natively without additional strategy work)

h3. Acceptance Criteria (Proposed -- requires PM/Engineering validation)

* Given a RHOAI OGX distribution is deployed, when a user configures {{provider_type: remote::anthropic}} with a valid Anthropic API key, then inference requests to Claude models return valid responses.
* Given the Anthropic API uses {{x-api-key}} + {{anthropic-version}} headers, when the {{remote::anthropic}} provider sends requests, then authentication succeeds without {{network.headers}} configuration, measured by successful HTTP 200 responses.
* Given a user sets {{anthropic_api_key}} in the {{x-ogx-provider-data}} header, when a request is sent, then the per-request API key overrides the config-level key, measured by successful authentication with a different key.
* Given a user requests model listing via {{/v1/models}}, when the Anthropic provider is configured, then Anthropic models are listed correctly using the {{AsyncAnthropic}} SDK format.
* The {{remote::anthropic}} provider is listed in the output of {{/v1/providers}} endpoint on a deployed OGX distribution.
